## 性能优化：上百个小文件上传极慢
- 文件：`apps/desktop-ui/src/App.tsx`（`uploadFiles`）、`src-tauri/src/main.rs`（`upload_local_file`/`upload_file`/`upload_directory` + 新增 `stream_upload_file`）
- 根因：每个文件后端都要 `channel_open_session` + `exec(cat)` + `eof` + `wait` + `close` + 再 `stat` 校验 = ~6-10 次 SSH 往返；前端 `uploadFiles` 又**逐文件串行 `await`**，几百个小文件的上百次往返延迟积少成多（XShell 用 SFTP 并发传输，故快很多）。
- 修复：
  1. 前端 `uploadFiles` 改为**有界并发池（CONCURRENCY=8）**：抽 `uploadOne` + 共享单个 `upload-progress` 监听（按 transfer_id 映射记录），多 worker 并行上传。
  2. 后端新增 `stream_upload_file`（文件→`cat > path` 单通道流式），`upload_local_file` 与 `upload_directory` 复用之；**去掉每文件多余的 `stat` 二次校验往返**（`cat` 退出码 0 已能确认写入完整，disk full 等也会非 0 退出）。
  3. 后端 `upload_directory` 改为「先遍历建目录并收集文件任务 → 用 `tokio::sync::Semaphore`(并发=6) + `tokio::spawn` 并发上传」（`cargo check` 通过）。
- 现状：拖拽多文件（走前端并发）与选文件夹（走后端 `uploadDirectory` 并发）两条路径均已并发化。

## 功能：上传并发数按本地 CPU 占用动态调整（高=1 / 不高=2）
- 文件：`src-tauri/src/main.rs`、`apps/desktop-ui/src/App.tsx`、`apps/desktop-ui/src/api.ts`
- 背景：用户先后把并发从 8/6 → 4 → 2，最后要求"根据实时情况，CPU 占用高就 1、不高就 2"。
- 实现：
  - 后端新增 `recommended_upload_concurrency(state: &AppState) -> usize`，复用既有的 `local_sys_monitor`（`sysinfo` 缓存实例）：首次调用两次采样（sleep 500ms 建基线）、后续调用一次 `refresh_cpu_usage()`，读 `global_cpu_usage()`；阈值 `CPU_BUSY_THRESHOLD = 60.0`（taskmgr 风格总占用），≥60 返回 1，否则 2。
  - 新增 Tauri 命令 `get_upload_concurrency`（sync，注册进 handler），供前端查询。
  - 后端 `upload_directory` 的 `concurrency` 不再写死 2，改为调用 `recommended_upload_concurrency(&**state)`。
  - 前端 `uploadFiles` 开头 `await getUploadConcurrency()`（api.ts 新增封装）决定并发池大小，失败回退默认 2；范围钳制到 [1,2]。
- `cargo check` 通过，前端 lint 0。
- 注：上传本属网络 I/O，CPU 占用通常非瓶颈；此动态调整主要避免高负载时再叠加并发，实际提速意义有限，但满足用户诉求。阈值 60% 若想调整改 `CPU_BUSY_THRESHOLD` 即可。

## 修复：大文件上传卡在 ~2MB 不动（SSH 双向流控死锁，严重 bug）
- 现象：`stream_upload_file` 上传 >2MB 文件时进度永久卡在恰好 ~2.0 MB / 总大小（如 47MB 卡在 2.0MB）；小文件（<2MB）正常。与并发数（1/2/动态）无关——并发调整只是被小文件现象掩盖，未触及真正根因。
- 根因：经典 SSH 双向流控死锁。上传时只往通道写（`cat > file`）而完全不读 server→client 方向。OpenSSH 在输出窗口被填满且客户端不消费时，停止读 input 且不再发 WINDOW_ADJUST；客户端写窗口在初始 ~2MB 耗尽后永久挂起（ChannelTx 窗口=0 时 notify.notified() 永久等待）。小文件在耗尽前 EOF 故正常。
- 修复：`stream_upload_file` 用 channel.split() 拆读写半边，在 tokio::spawn 后台任务里持续 reader.wait() 排空输出（丢弃 Data/ExtendedData，捕获 ExitStatus），主循环继续 writer.data() 写；传完 eof()+close() 后 await reader 任务取退出码判成败。输出窗口持续流动 → 服务端恢复发 WINDOW_ADJUST → 大文件可正常传完。
- russh 0.51 调试线索：Channel::data 走 channels/io/tx.rs 的 ChannelTx（按窗口等 Notify）；WINDOW_ADJUST 处理在 src/{client,server}/encrypted.rs，库本身正确，问题在使用方式（上传期间不消费输出）。
- cargo check 通过。
